# Резидентский резерв Dropo

Для пользователя точкой выбора остаётся профиль Dropo Free или Dropo Turbo. В режиме автоматического подключения приложение проверяет входы по ступеням. Успех означает ответ HTTPS через соответствующий туннель. Открытого TCP-порта для этого недостаточно.

| Очерёдность | Dropo Free | Dropo Turbo |
| --- | --- | --- |
| 1. Москва | Три метода через Москву с выходом в Латвии | Три метода через Москву с выходом в Финляндии |
| 2. Напрямую | Три метода на латвийском узле | Три метода на финском узле |
| 3. Домашний шлюз | Выданный IPv4, TCP 34443 → Латвия | Выданный IPv4, TCP 34444 → Финляндия |

У первых двух ступеней доступны XHTTP, TCP/REALITY и Hysteria 2. В меню **Ещё** видны методы и результаты замеров. В автоматическом режиме рабочие методы одной ступени ранжируются по отклику. Клиент пробует следующую ступень, когда подходящих входов на предыдущей нет. У резерва свой вход, но выходной регион, аутентификация тарифа и правила доступа сохраняются. При двух включённых управляемых профилях клиент исчерпывает московские варианты обоих тарифов перед переходом к прямым, затем пробует домашние. После установления связи сохраняет выбранный вход до отказа или нового подключения. Сбой самого регионального выхода затронет все три ступени этого тарифа.

## Кто кого видит

Домашний сервер доступен администратору по закрытому адресу Tailscale. Подписчику достаточно установленного Dropo и активного профиля. Приложение получает одно назначение на тариф. В каталоге и протоколе подключения нет списка устройств или механизма связи между клиентами. Пользовательское соединение доходит до слушателя на физическом интерфейсе домашнего сервера. Каждый слушатель пересылает TCP в единственный заранее заданный региональный сервис. Клиент проверяет TLS-сертификат этого сервиса, а региональный узел проверяет его VLESS-реквизиты.

Владелец активной подписки и сеть, из которой устанавливается соединение, технически могут узнать домашний IP. Раздельные ключи и подпись защищают выдачу и подлинность адреса. Общий физический адрес остаётся блокируемым, а пропускная способность обоих резервов ограничена домашним подключением. При отказе домашнего интернета остаются две старшие ступени.

## Выбор способа выдачи

| Вариант | Когда подходит | Последствие для Dropo |
| --- | --- | --- |
| Индивидуальное подписанное назначение по HTTPS | Клиенту достаточно получить один актуальный адрес своего тарифа | Используется существующий профиль и транспорт Dropo. У каждого устройства свой ключ. Это реализованный вариант. |
| Общая сеть Tailscale с правилами доступа | Устройства должны обмениваться трафиком с несколькими частными сервисами | Потребуются дополнительная регистрация устройств, правила доступа и доступность прямого соединения или ретранслятора. Для этого проекта Tailscale обслуживает администрирование. [Соединения Tailscale](https://tailscale.com/kb/1082/firewall-ports) |
| DNS с динамическим обновлением | Приемлемо открытое обнаружение единого сервера | Имя удобно для оператора. Адрес доступен любому, кто знает имя, а выдача зависит от DNS и кэшей. Самостоятельного контроля тарифов у A/TXT-записи нет. |

WireGuard предоставляет VPN-протокол и программы для клиентских платформ. Доступность конкретного IP и UDP-маршрута определяет сеть абонента. Покупка услуг у провайдера на базе WireGuard не даёт технической гарантии связи с домашним узлом. [Описание протокола WireGuard](https://www.wireguard.com/)

## Как меняется адрес

1. Служба на домашнем сервере получает внешний IPv4 от домашнего маршрутизатора. Каждые 90 секунд после завершения предыдущей проверки она продлевает две собственные записи перенаправления на 600 секунд и сверяет их с фактическими записями маршрутизатора. Требуются публичный IPv4 и входящая связность. Конфликт чужого перенаправления останавливает обновление.
2. С ключом публикации шлюз вызывает единственную разрешённую команду `announce`. Приёмник берёт адрес источника из SSH-соединения, подключается к обоим портам извне, проверяет имя регионального TLS-сервера и согласование HTTP/2. Только после успеха обеих проверок он атомарно заменяет подтверждённую запись. Домашний ключ не может подписывать клиентские назначения.
3. Когда требуется третья ступень, клиент запрашивает назначение по HTTPS через три адреса доставки. Финский адрес доступен в обход московских точек. Все три обращаются к одному контроллеру. Действующая запись на устройстве покрывает короткий отказ каталога. Первая регистрация без ранее выданных реквизитов по-прежнему требует доступности штатного сервиса регистрации.
4. Контроллер проверяет право установки на Free или Turbo. Ответ содержит назначение, тариф, время подтверждения и срок. Контроллер подписывает ответ Ed25519 и шифрует AES-256-GCM с ключом, выведенным из индивидуальных региональных реквизитов установки. В публичном DNS сведения о домашнем адресе не размещаются. Доверенный ключ проверки встроен в клиент.
5. Клиент проверяет подпись, тариф, индивидуальный идентификатор, порт и срок. Локально сохраняется шифротекст. Запись моложе двух минут клиент может использовать сразу. При отказе TCP он запрашивает адрес повторно и пробует новый IP. Предельный срок с последней проверки шлюза составляет восемь минут. Для Turbo он дополнительно ограничен окончанием подписки. После смены IP следующий запрос использует опубликованное назначение. Уже открытые соединения со старым адресом могут потребовать переподключения.

## Где это реализовано

| Компонент | Исходники |
| --- | --- |
| Построение семи входов из управляемой подписки | `app/mobile/dropocore/ownedprofile` |
| Подпись, расшифровка, кэш и повторный запрос в клиенте | `app/mobile/dropocore/residential` |
| Выбор ступени в Android и сокет вне VPN | `app/mobile/dropoandroid/source_selection.go`, `xhttp_dialer.go`, `xhttp_runtime.go` |
| Выбор ступени в Windows и соединение через физический интерфейс | `app/core_vpn_source_latency.go`, `core_vpn_source_monitor.go`, `residential_bridge.go`, `residential_dial_windows.go` |
| Выдача и эксплуатация в репозитории vpn-servers | `infra/control/residential.go`, `infra/residential/` |

На Android Xray использует сокет, защищённый через VPN-сервис платформы. На Windows локальный TCP-слушатель привязан к VPN-сессии приложения и закрывается при её завершении. Домашнее назначение перехватывается до системного DNS. Для iPhone и macOS интеграции потребуются в Packet Tunnel Provider, для Linux — в маршрутизации физических сокетов вне TUN. Всем платформам подходит один формат выдачи. Готовые клиенты этой реализации собираются для Android и Windows.

## Проверка, развёртывание и откат

1. На домашнем узле установить системный пакет `python3-miniupnpc`, запустить `infra/residential/install-gateway.sh` с именем физического интерфейса. Два сокета передают данные как есть. Шлюз допускает до 256 TCP-соединений на тариф.
2. На узле каталога установить `receive.py` как исполняемую команду под контролем администратора. У выделенной учётной записи публикации должен быть доступ на запись в `/var/lib/dropo-residential-feed`, у контроллера — на чтение. Привязать открытый ключ шлюза в OpenSSH к этой команде с `restrict`. На шлюзе в `/var/lib/dropo-residential/publisher` описать SSH-псевдоним `dropo-directory`, отдельный ключ и проверенный ключ сервера. Закрытые ключи остаются на соответствующих машинах.
3. Установить контроллер с индексом поиска назначений. Для независимого входа включить `infra/residential/directory.location` в HTTPS-сервер `dropo.fun`, проверить конфигурацию командой `nginx -t` и перезагрузить конфигурацию. Клиент с активной подпиской должен получить подписанное назначение, отозванная установка — HTTP 404, устаревшая запись шлюза — HTTP 503.
4. На повторном развёртывании проверить `systemctl is-active dropo-residential-{free,boost}.socket dropo-residential-renew.timer` и `systemctl show -p Result dropo-residential-renew.service`. Выполнить `python infra/residential/verify.py --node lv1` и проверку с разрешённого московского IP. Скрипт создаёт временный профиль, проверяет HTTPS, UDP, выходной IP и отказ в доступе к частному адресу, затем отзывает временный профиль. Запуск требует штатных административных реквизитов проверки.
5. До массовой публикации испытать обновление существующего профиля в российских фиксированной и мобильной сетях. На тестовом устройстве последовательно отключить доступность московских и прямых входов, сохранить доступ к каталогу, подтвердить «Резервный шлюз» и выход тарифа. Отдельно проверить восстановление после смены внешнего IP и холодный старт после истечения кэша. Смену WAN на рабочем домашнем маршрутизаторе лучше проверять при очередной естественной смене адреса.
6. Для отключения резерва на домашнем узле выключить таймер, остановить службу обновления, выполнить `/usr/bin/python3 /usr/local/lib/dropo-residential/gateway.py --remove`, отключить оба сокета и остановить оба прокси-сервиса. На контроллере отозвать ключ публикации и убрать `verified.json`. Каталог прекратит выдачу, оставшийся кэш истечёт максимум за восемь минут. Если требуется убрать и точку выдачи, удалить только её включение из конфигурации Nginx, проверить и перечитать конфигурацию. Это сохраняет московские и прямые методы.

Проверка 24 ноября 2026 года подтвердила оба тарифных маршрута с узла в Латвии и с одного из двух исходящих адресов московского дата-центра. На втором московском адресе установление TLS завершилось по тайм-ауту. Внешняя проверка каталога из Финляндии подтверждает доступность для публикации. Опыт конкретного российского абонента зависит от маршрута его оператора.

На Android проверка запускала настоящий VpnService отдельно для Free и Turbo. Временные правила внутри эмулятора делали недоступными московские и прямые входы, а также две московские точки каталога. Приложение выбрало `residential-xhttp` у обоих тарифов. Через туннель прошли HTTPS, UDP и DNS с выходом в нужной стране. Эмулятор и Windows находились за тем же домашним маршрутизатором, что и шлюз. Обращение к собственному публичному IP из дома не прошло. Для локального испытания возврат на домашний слушатель имитировался в тестовой среде. Работоспособность внешнего перенаправления независимо проверена с реальных удалённых узлов.

На Windows отдельно проверены расшифровка рабочего назначения, подключение через выбранный физический интерфейс, сертификаты обоих регионов и HTTP/2 при имитации возврата внутри LAN. После отзыва тестовых прав каталог вернул HTTP 404. Функциональный тест смены IP проверяет повторную выдачу, подключение к новому адресу и отказ при непродлённом старом адресе. Фактическое переподключение WAN провайдера в ходе испытания не производилось. Полный сеанс Windows в Hyper-V и приёмка из российских абонентских сетей остаются непроверенными в этом испытании.
